# PS-425 — Multi-shipment lifecycle and billing cardinality

## Placement decision

- Business rule: every distinct active outbound shipment is independently billable; voided labels and return labels are excluded. An order may reopen only after its final active outbound shipment is voided and no upstream/external terminal evidence remains.
- Canonical owner: `src/services/shipment-aggregate.ts` (`activeOutboundShipmentPredicate`, `withShipmentBillingLineage`, and `decideShipmentVoidLifecycle`).
- Billing owner: `src/services/billing.ts` consumes the canonical active set and persists one frozen line per shipment. Generated counts and totals come only from inserted rows returned by PostgreSQL.
- Lifecycle owner: the label-void transaction locks the order, marks the target shipment voided, reads the remaining canonical active set, and delegates the status decision to `decideShipmentVoidLifecycle`.
- Current unsafe owners removed: the order-level `billing_li_unique` conflict-drop and the unconditional `orders.order_status = 'awaiting_shipment'` void write.
- Imperfect-data injection points: multiple valid outbound shipments joining one order, provider/worker duplicate shipment rows, return shipments joining outbound billing, voided replacement rows, and a partial void observing only its target shipment.
- Duplicate/replacement/return treatment: provider duplicates remain blocked by `shipments_label_shipment_id_unique_idx`; voided/replaced labels and returns are excluded by the aggregate predicate; a distinct active replacement/outbound shipment remains independently billable.
- Callers that delegate: billing generation and label void. HTML, XLSX, and CSV consume shipment-scoped frozen invoice rows and display the shipment identity.
- Forbidden wrapper logic: no frontend cardinality, lifecycle, margin, or export-total calculation; no route-level shipment selection; no conflict-ignore fallback.
- Frontend role: display/action only. No frontend change was required.

## Migration and frozen-data behavior

`drizzle/0068_billing_shipment_cardinality.sql` replaces the old order-level unique constraint with:

- `billing_li_shipment_unique_idx` for shipment-backed lines;
- `billing_li_order_unique_idx` for shipment-less order/external lines;
- the existing storage period key remains authoritative for storage rows.

The migration rewrites no billing rows. PS-412 finalized-row triggers and close records are unchanged. Existing finalized data is not regenerated.

## Verification contract

`npm run test:ps-425-multi-shipment-cardinality` proves offline that:

- two active shipments with distinct internal costs persist two customer-charge lines;
- `RETURNING` count/total equals the database count/total;
- a duplicate candidate fails loudly;
- shipping margin preserves both shipment identities and reconciles internal cost, customer charge, and margin;
- HTML, XLSX, and CSV show the same two shipment rows and charges;
- returns, voided replacements, and provider duplicates are excluded;
- the first void keeps the order shipped, the final void may reopen it, and upstream/external terminal evidence prevents reopening.

No test contacts a carrier/marketplace, buys postage, creates a real label, regenerates production billing, or mutates production shipped/cancelled rows.
