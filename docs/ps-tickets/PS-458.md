# PS-458 — Canonical frontend endpoint caches

## Placement

- **Canonical owner:** Backend endpoints remain authoritative for every DTO and
  business value. `web/src/lib/endpoint-query-keys.ts` owns frontend request
  identity, while the singleton `queryClient` owns dedupe, freshness, retention,
  and stale-data behavior.
- **Imperfect-data entry point:** Duplicate or stale frontend state first entered
  when a view-specific TanStack key, the legacy `cachedReads` map, and the
  Packages module cache stored the same GET independently.
- **Caller delegation:** Dashboard, Billing, Settings, Orders, Inventory,
  Packages, sidebars, and shared hooks now use the endpoint key factory. Raw
  adapter methods transport and normalize responses but do not cache them.
  Client create/update/delete/toggle/sync paths delegate to
  `web/src/lib/client-cache-invalidation.ts` instead of maintaining per-view
  invalidation lists.
- **Mutation consistency proof:** The real Clients-page mutation callbacks and
  the shared API client both invalidate the same client, store, count, and
  inventory families through one owner. The obsolete `['inventory']` alias is
  rejected by the PS-458 guard. Dashboard and Orders consume those canonical
  families, so an active-state change cannot leave one view on stale client
  scope. Package and billing mutations invalidate only their canonical endpoint
  roots.
- **Safety:** This is frontend cache architecture only. It changes no backend
  business rule, database schema/data, shipped/cancelled protection, billing
  calculation, rate/label behavior, provider call, or production data.
