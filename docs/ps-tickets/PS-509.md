## Packet item 4 — canonical code trace (read-only, complete)

Traced at `0376ab2d`. No code changed.

### Call graph — a single funnel

```
sync-job-queue.ts:1555
  └─ syncShipments()                 shipment-sync.ts:787   (only caller)
       └─ upsertShipmentsBatch()     shipment-sync.ts:191   (only caller, line 890)
```

**`upsertShipmentsBatch` is the canonical sync insert/update owner.** One caller each way, no alternate entry point, and no raw-SQL `insert into shipments` anywhere in `src/`. This is the single seam PS-509 needs.

### Stage 1 — payload → scope filter

`partitionShipmentsByStoreScope` (:214) drops `EXCLUDED_STORE_IDS` at the ingest funnel, so excluded stores never create a row at all.

### Stage 2 — normalization

`shipmentValues(s, orderId, clientId)` (:142-171) builds the row. **What it does NOT produce matters as much as what it does:**

| written | not written |
|---|---|
| `cost` (`s.shipmentCost`) | `otherCost` |
| `carrierCode`, `serviceCode`, `trackingNumber` | `selectedRateCost` |
| `voided` (`s.voided`), `isReturn` | `selectedRateJson` |
| `source: 'shipstation'` (hardcoded) | |

### Stage 3 — order lookup and the existing-row split

`orderSourceIdentityOrLegacyPredicate` resolves the order. Rows then split on whether a row with the same `labelShipmentId` exists.

**UPDATE branch (:418-450)** applies field-level preservation — never null `orderId`/`clientId`, never rewrite `source`. That last one matters here: **a row PrepShip created keeps `source = 'prepship_v2'` even when sync updates it**, so sync updates can and do run over rows the PS-508 writer produced.

**INSERT branch (:451-474)** is the only place authoritative cost is stamped:

```ts
values.otherCost = toNumeric(s.insuranceCost) ?? '0.00';
values.selectedRateCost = resolveBillingSelectedRateCost({
  cost: values.cost, otherCost: values.otherCost, selectedRateJson: null,
})?.toFixed(2) ?? null;
```

Rows with an unresolvable order are recorded as `unattributed` (:467-473) rather than accepted silently.

### Stage 4 — first authoritative cost: INSERT ONLY

`selected_rate_cost` is written **on INSERT and never on UPDATE**, by deliberate design (:445-449): the update `SET` omits `otherCost`, so writing cost-only would drop a labelled row's insurance and change its billed total.

**Therefore the first authoritative cost exists exactly once per row, at insert.** That is the natural freeze point, and it is the direct analogue of `persistCreatedLabel`.

### Stage 5 — transaction boundary: **ASYMMETRIC**

This is the most consequential finding for PS-509.

| path | boundary |
|---|---|
| **INSERT** (:514) | inside `db.transaction`, chunked 500, with per-inserted-row work already running inside `tx` |
| **UPDATE** (:633-637) | **no transaction** — `db.update(...)` fired 3-at-a-time through `Promise.all`, each autocommitting independently |

PS-509 requires that "tuple and authoritative shipment receipt commit atomically." That is **achievable on the insert path** — the transaction exists and already hosts per-row work — and **not achievable on the update path as written**, where there is no transaction to join. Any tuple work on updates would be a separate autocommitted write, or would require introducing a transaction the concurrency-3 design deliberately avoids (Supabase pgbouncer tops out at 15 shared connections).

### Stage 6 — replay, correction, void

**Replay is already idempotent, and the primitive is strong.** `labelShipmentId` is UNIQUE, and the insert uses:

```ts
.onConflictDoNothing({ target: [shipments.labelShipmentId],
                       where: sql`${shipments.labelShipmentId} is not null` })
.returning({ ... })
```

`.returning()` yields **only genuinely inserted rows**. A replay produces an empty set, so a freeze driven off `insertedRows` cannot reprice — replay-safety comes free from the existing shape rather than needing new machinery.

**Correction is the open hazard.** `shipmentValues` writes `cost` on UPDATE but never `selected_rate_cost`. So when ShipStation revises a shipment's cost:

- `cost` changes;
- `selected_rate_cost` keeps its original value;
- any frozen tuple keeps its original value.

The carrier receipt and the frozen money then disagree, and nothing detects it. Today that is contained because no sync row carries a tuple. **After PS-509 it becomes a live divergence source**, and the packet must decide: re-freeze under a correction rule, flag for review, or explicitly accept the original as immutable.

**Void arrives the same way.** `voided: Boolean(s.voided)` is written on UPDATE, so a void can land on a row that already carries a tuple. Needs an explicit rule.

## Packet item 5 — contemporaneous facts at first ingestion (complete)

What the sync path actually possesses at the freeze point (the INSERT), from the `SSShipment` v1 payload, the schema, and a production run at `ff93e3b2`:

| fact | at the insert? | evidence |
|---|---|---|
| final purchased cost | **yes** | `shipmentCost` → `cost`; `selected_rate_cost` stamped on new rows since PS-381 (2026-07-06) |
| insurance | **yes** | `insuranceCost` → `otherCost` (`'0.00'` when absent) |
| label purchase timestamp | **yes** | payload `createDate` → `create_date` |
| client / store identity | **mostly** | order lookup at ingestion; 7.7% unattributed; store id via `advancedOptions.storeId` (used by the scope filter) |
| purchased-provider identity | **NO** | the v1 payload carries no provider/payer field; `provider_account_id` arrives via a later best-effort V2 enrichment keyed on tracking number — the same written-later-by-a-task-allowed-to-fail shape as the PS-508 house sidecar. Empirically it lands completely (5,066/5,066 resolved in the window), but never at the insert |
| customer policy (markup / HUGRAB / reference / house) | **present-day only** | `billing_config` / `order_overrides` are read-at-now; **no history table exists anywhere in `src/` or `drizzle/`**, so purchase-time policy is unprovable retroactively |

**Measured purchase → ingestion lag** (`created_at` − `create_date`): last-7-days **p50 138s, p90 281s, p99 777s (~13 min)** — consistent with the 3-minute scheduler. Whole-window p99 (~9.4h) reflects backlog walks and column-backfill artefacts, not steady state.

**Carrier distribution:** `stamps_com` 3,271 · `ups` 1,487 · `ups_walleted` 303 · `fedex_walleted` 5 — **no `shipp`**. House eligibility for this ingress is by construction never (a synced row is not a SHIPP-direct purchase), and the data agrees.

**Item-5 conclusion for the packet:** Hermes's bar for calling a freeze "purchase-time" is proving the policy facts *existed and were stable* at purchase. Existence at ingestion: yes. Stability across the gap: **unprovable** — no policy history exists — even though the measured gap is minutes. The packet should therefore take Hermes's explicit alternative branch: a **named `sync_ingestion` provenance with honest timing**, noting the steady-state gap is minutes. House inputs are moot for this ingress.

## Packet item 6 — redacted samples, and what they revealed (complete)

Three newest rows per eligibility class, shape only (no order/tracking identifiers), from the same run. Full table in the Actions log of run `32241251024`.

```
positive_cost_attributed:  cost 9.23  sel 9.23  order y  provider y  lag 62–252s   line N
no_selected_cost:          cost 5.88  sel null  order y  provider y  lag 382–846s  line y
return:                    cost 8.64  sel 8.64  order N  provider y  lag 11–529s   line N
unattributed_no_order:     cost 5.70  sel 5.70  order N  provider y  lag 103–326s  line N
voided:                    cost 7.75  sel 7.75  order y  provider y  lag 59–221s   line N
```

### The finding: `no_selected_cost` is a legacy stamping gap, not unpriceability

The samples show the bucket's rows carry **positive `cost` with `selected_rate_cost` null — and existing billing lines**. And because the sample ranking is `id desc`, the top sample **is** the bucket's maximum id: **the newest `no_selected_cost` row is id 27585**, against a newest overall id of 30744.

The bucket **stopped being produced** — at exactly the PS-381 boundary (2026-07-06), when sync began stamping `selected_rate_cost` on new rows (new rows only, deliberately, to avoid rewriting historical truth). So the 2,277 rows are **pre-PS-381 history**: priced today by billing's read-time fallback (`resolveBillingSelectedRateCost` falls back to `cost + otherCost`), which is why they carry lines.

**This answers the packet's largest open question.** Consequences:

1. **Going forward, the candidate population is effectively all attributed, non-void, non-return sync rows** — new sync inserts all receive `selected_rate_cost`.
2. The 2,277 belong to PS-508's **evidence-qualified historical handling**, not to PS-509's writer — and they carry contemporaneous carrier-cost evidence (`cost`), which places them in the "evidence exists" partition rather than the unresolvable one.
3. `zero_or_negative_cost` did not appear as a bucket in production at all.

## What the trace settles

1. **Canonical owner identified** — `upsertShipmentsBatch`, single funnel, no alternate writers.
2. **The freeze point is the INSERT branch**, where the first authoritative cost is stamped and a transaction already exists.
3. **Replay safety is inherited** from `onConflictDoNothing` + `.returning()`.
4. **The update path cannot offer atomic commit** without a design change it currently avoids on purpose.
5. **Correction and void reach rows through UPDATE**, which is exactly the path that cannot freeze atomically — so those rules cannot simply mirror the insert rule.

## What the trace does NOT settle

- **Billability.** Still the blocking product-owner decision. Source name cannot decide it.
- ~~Contemporaneous policy facts~~ — settled by item 5: unprovable (no policy history table); the packet takes the named `sync_ingestion`-provenance branch.
- ~~Purchased-provider identity~~ — settled by item 5: absent at insert, arrives post-hoc via V2 enrichment; and no `shipp` carrier exists in the sync population, so house eligibility for this ingress is never.

## Note for PS-508

Sync UPDATE cannot clobber a frozen tuple **today**, because `shipmentValues` omits `selectedRateJson` and `selectedRateCost`. That is a property of the current helper, **not an enforced constraint** — adding either field to `shipmentValues` would silently overwrite frozen customer money. Worth a guard before cutover.
