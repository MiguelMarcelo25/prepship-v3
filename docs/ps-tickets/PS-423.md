# PS-423 — Durable provider-operation ledger

Status: implemented locally for PrepShip and Client Portal; migration-first
deployment and final-review movement remain pending locked-file push approval.

## Architecture placement

- **Business rule:** a provider mutation may execute once for one semantic
  operation. Only a proven pre-dispatch failure may retry automatically. A lost
  or ambiguous response stays held until a provider receipt or an explicit
  operator no-effect resolution exists.
- **Canonical owner:** `src/services/fulfillment-operation-ledger.ts` plus the
  additive `external_operations` table from
  `drizzle/0072_external_operations.sql`.
- **Imperfect-data entry points:** provider timeout after submission, process
  death after provider success but before local persistence, stale worker
  completion, asynchronous Shopify purchase polling, outbox ACK before local
  settlement, and concurrent duplicate requests.
- **Delegating callers:** forward ShipStation/direct labels, Shopify Shipping
  purchase and polling, ShipStation returns, provider voids, Print Queue through
  the existing label owner, manual/external marketplace confirmation, and the
  fulfillment confirmation outbox.
- **Thin adapters:** carrier/store connectors translate provider payloads and
  receive `AbortSignal` plus the stable idempotency key where supported. They do
  not decide whether a retry is allowed.
- **Forbidden duplicate owners:** new `label_purchase_intents` writes, frontend
  retry policy, connector-local retry admission, and local shipment/order state
  changes before a durable provider receipt.
- **Frontend role:** none. No React code calculates or authorizes provider
  mutations.

## State machine and invariants

`prepared -> in_flight -> receipt_recorded -> consumed`

- `failed_pre_dispatch` is the only automatically claimable retry state.
- `reconcile_required` is a hard hold.
- Every claim increments `generation` and owns a random `lease_token`.
- Heartbeats extend the lease; cancellation is requested and acknowledged
  through the shared durable-attempt owner.
- Provider receipts and local results are redacted and size bounded.
- Receipt consumption and the local shipment/lifecycle or outbox settlement
  commit in one database transaction.
- Operator resolution increments generation, fencing any late old worker.

## Implemented surfaces

- Forward ShipStation and direct carrier labels record receipts before shipment,
  package, inventory-claim, and shipped-lifecycle persistence.
- Shopify pending and terminal purchase results use one durable operation; poll
  errors retain the existing purchase instead of marking it safe to rebuy.
- Return-label postage is receipt-first and replay-safe; the compatibility
  `return_labels` mirror avoids duplicate rows on consumed retries.
- Provider voids leave the shipment active locally when the result is unknown.
- Marketplace confirmation receipts settle the outbox, shipment confirmation,
  and order canonical status atomically.
- Admin APIs list held operations and accept only audited provider receipt or
  provider-verified no-effect resolutions.
- Migration runners and Render one-off workflows verify the additive schema
  before application deployment.

## Client Portal return alignment

Client Portal CP-057 remains a return-specific compatibility coordinator; the
canonical purchased label/rate/tracking truth stays on `shipments`. PS-423 adds
generation fencing, renewable leases, abort propagation, and an admin no-effect
resolution. A provider lookup returning 404 no longer authorizes an automatic
repurchase.

## Shipped/cancelled override and safety proof

Per user override `unlock shipped data` on 2026-05-23, the protected workflow
files changed are:

- `src/services/labels.ts` — receipt-first forward/Shopify/return/void handling
  and atomic local consumption.
- `src/services/fulfillment/outbox.ts` — receipt-first marketplace confirmation
  and atomic confirmation settlement.

The override was necessary because both owners insert/read `shipments` and
settle shipped order lifecycle. The change does not remove or weaken
`LOCKED_STATUSES`, `assertOrderEditable`, `isReadOnly`, the inventory kill
switch, shipment history, or any shipped/cancelled edit gate. No schema column
was dropped or renamed, and migrations contain no `UPDATE`/`DELETE` against
`orders` or `shipments`.

No configured database/provider was contacted. No real label, postage,
marketplace/customer notification, inventory movement, production shipment, or
production shipped/cancelled mutation occurred during verification.
