# PS-452 — Print Queue lifecycle: reaper, attempt caps, chunking, cancel-on-timeout

## Source-of-truth placement

- `queue-send-job-store.ts` owns cross-process generation/chunk claims,
  heartbeats, stale-write fences, per-item attempt counters, and terminal parking.
- `queue-send-execution.ts` owns bounded chunk size, cooperative admission, and
  settle-before-release pool behavior.
- `print-queue-worker.ts` owns the periodic reaper, exact generation heartbeat,
  cancellation request/acknowledgement, recovery planning, and continuation CAS.
- `print-queue.ts` owns the per-order workflow. It claims the durable item and
  then delegates again to the canonical backend preflight immediately before
  the label/queue path; React does not decide editability or retry safety.

The earliest imperfect-data boundary is a worker/process failure after an order
is admitted but before the parent snapshot becomes terminal. PS-452 prevents an
old executor from writing after a replacement generation is claimed and keeps
unknown provider outcomes fenced for exact reconciliation.

## Runtime behavior

- Migration `0073_print_queue_send_execution_fences.sql` adds nonnegative
  generation/attempt counters, current chunk sequence, heartbeat and cooperative
  cancellation timestamps, plus the stale-recovery index. It changes only Print
  Queue orchestration sidecars.
- A worker may claim only `pending` plus the exact generation/chunk. A second
  replica receives zero rows and cannot enter the provider-capable module.
- Running work heartbeats every 15 seconds. The 60-second reaper uses the
  heartbeat for running jobs and atomically claims stale jobs with
  `FOR UPDATE SKIP LOCKED`.
- Each safe item is claimed atomically and may enter at most three interrupted
  executions. An exhausted safe item becomes `failed_terminal`; siblings retain
  their independent counters and continue. `provider_pending` and
  `provider_pending_recovery` are never terminalized or resent by this rule.
- A verified provider receipt moves to `receipt_resume` (or directly to
  `shipment_persisted`) with a fresh, separately bounded local-tail budget. This
  lets queue-only recovery finish even when the provider-attempt budget is
  exhausted, without purchasing a second label. Shopify pending receipts poll
  the existing operation to terminal; they do not issue another purchase.
  Caught database, polling, or queue-tail errors retain that phase until its
  third attempt, then park terminal instead of stranding after one failure.
  These ledger-proven local tails still run scope/status/safety preflight but
  ignore only an orphaned process purchase lock. Their dedicated receipt path
  forbids provider dispatch, and a persisted shipment with a missing artifact
  cannot fall through to a new purchase.
- A consumed historical operation is re-admitted only when its exact shipment
  is no longer active and the canonical outbound-shipment count proves the
  semantic generation has advanced (for example, relabel after a void). A
  missing same-generation shipment remains held rather than risking replay.
- Chunks contain at most 20 orders. At concurrency four and the 90-second
  provider timeout, the worst-case provider budget is about 450 seconds, leaving
  headroom inside the 10-minute worker deadline.
- Cancellation or an unexpected task failure stops new admissions, waits for
  every admitted sibling to settle, then releases the durable claim.
- The next chunk is reserved with a generation/chunk compare-and-swap before it
  is published. A null/failed publish becomes a visible interruption.
- Recovery has a separate hard 30-generation parent cap. At that cap only safe
  unfinished sidecars are parked; provider-ambiguous items retain their real
  reconciliation-required state.

## Certification

`npm run test:ps-452-print-queue-lifecycle` applies the real Print Queue table
block from migration 0062 plus migration 0073 to an in-memory PGlite database.
It proves exclusive claims, heartbeat/reaper behavior, generation-fenced parent
and item writes, three-attempt poison parking, sibling/provider-state isolation,
and continuation CAS.

The same test runs a 1,000-order, 50-chunk crash/recovery simulation. One poison
order crashes three generations and parks terminal; the other 999 orders queue
exactly once, progress stays monotonic, and repeat recovery admits zero orders.
A separate unknown-provider fixture remains held with zero provider replay.

Required regression gates include PS-400, PS-401, PS-403, PS-420, durable Print
Queue, PS-053 atomicity, PS-444 recovery safety, runtime-schema readiness,
TypeScript typecheck, and the production build.

The crash fixture injects failure at the same durable boundaries and exercises
the real migration/store SQL in PGlite. It is not an operating-system kill of a
live pg-boss worker and does not wait through the real 60-second cadence because
this workstation has no local Postgres runtime. Exact-SHA post-deploy health and
reaper observation remain required release evidence; this limitation is not
represented as live-process proof.

Before deploying the runtime, inspect/apply migration 0073 with the guarded
`migrate:ps-452-print-queue-lifecycle` command and its explicit confirmation
token. Runtime-schema readiness then fails closed if any required fence column
or recovery constraint/index is missing. The migration must be applied before
the PS-452 runtime is deployed because that runtime intentionally fails closed
without the execution fences.

## Rollback and roll-forward

- Application rollback is forward-compatible: redeploy the previously healthy
  application while leaving migration 0073's additive sidecar columns,
  constraints, and index in place. Existing defaults preserve older inserts.
- Do not drop the new columns/constraints/index during an incident, and do not
  delete or reset Print Queue jobs, provider operations, orders, or shipment
  history. Schema rollback is deliberately non-destructive.
- Roll forward by correcting the application, re-running the offline gates, and
  deploying the reviewed exact SHA. Runtime readiness verifies every required
  column, four named constraints, and the stale-recovery index before traffic.
- Post-deploy certification must prove exact-SHA parity, deep health, worker
  heartbeat/reaper health, terminal error visibility with no Resume action, and
  no unexpected provider replay.

## Shipped-data override and safety

Per user override `unlock shipped data` on 2026-07-21, the protected Print Queue
workflow may be changed for PS-452. The shipped/cancelled edit locks are not
weakened: execution-time backend preflight now re-checks them closer to the
provider boundary. No SQL in this ticket updates/deletes `orders` or
`shipments`; no schema column in those tables changes.

All certification is offline. It performs no real label purchase, postage,
printing, provider call, marketplace notification, inventory mutation, or
production shipped/cancelled mutation.
