# PS-427 — One-sided inventory cache reconciliation

## Architecture placement

- **Business rule/workflow:** reconcile a drifted inventory cache to canonical movement history exactly once without changing movement history.
- **Canonical owner:** `src/services/inventory-reconciliation.ts` (`buildInventoryReconciliationPlan` and `applyInventoryReconciliationPlan`).
- **Canonical quantity input:** `src/services/inventory-stock-math.ts` (`computeEffectiveStockForIdsInTransaction`).
- **Unsafe former owner:** `POST /admin/reconcile-inventory-stock` derived a delta inline and passed it to the normal movement primitive, which incremented both `inventory_ledger` and `inventory.stockQty`.
- **Earliest imperfect-data injection:** the former admin apply call created a new ledger adjustment from the ledger/cache gap and then applied the same adjustment to the cache, preserving the gap instead of repairing it.
- **Callers that delegate:** the admin route validates transport/auth intent and delegates plan/apply decisions to the reconciliation service.
- **Duplicate logic removed/forbidden:** the route no longer contains effective-stock SQL and reconciliation must never call `applyInventoryMovementInTransaction` or append a quantity ledger row.
- **Frontend role:** none. Any future UI may render the backend plan/result and submit operator intent only.
- **Boundary proof:** `test:ps-427-inventory-reconciliation` exercises the service against isolated PGlite and statically rejects a movement-based repair.

## Contract selected

`inventory_ledger` is authoritative. `inventory.stockQty` is a cache. A reviewed repair sets only the cache to the ledger-derived balance. It does not add an `adjust` movement.

Dry-run returns a deterministic plan hash over the exact scope and before/authoritative values. Apply requires:

- exact `clientId` and case-insensitive exact `sku` scope;
- the unchanged reviewed plan hash;
- an authenticated actor, reason, and separate approval reference;
- the exact confirmation phrase; and
- `INVENTORY_RECONCILIATION_APPLY_ENABLED=true`, which defaults off.

Case-variant duplicate SKUs within a client block the whole scope. Apply locks scoped cache rows, recomputes canonical ledger truth in a serializable transaction, writes absolute `stockQty`, and inserts required append-only `audit_log` rows in that same transaction. Audit details contain before, authoritative/after, reviewed scope, plan hash, approval, and `rollbackStockQty` evidence.

## Safety and rollback

- No production repair is part of PS-427 development or deployment.
- No `orders`, shipped/cancelled rows, `shipments`, labels, billing, fulfillment, package, or provider state is mutated.
- The dry-run CLI remains read-only and intentionally has no apply mode.
- A failed audit insert or concurrent change rolls back the cache update.
- Operational rollback uses the immutable per-row `rollbackStockQty` evidence from the exact reconciliation run and requires a separately reviewed action; there is no blind rollback endpoint.

## Verification

- stock 10 / ledger 7 → cache 7, ledger unchanged; second plan has zero adjustments;
- reverse discrepancy, zero, and negative balances use the exact ledger value without clamping;
- duplicate/case-variant SKU scope fails closed;
- simultaneous reconciliation/movement leaves cache and ledger converged or rejects the stale plan;
- forced audit failure rolls back the cache update;
- default-off gate and legacy apply request fail closed.
