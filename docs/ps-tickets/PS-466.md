# PS-466 - Versioned Automations rules engine

## Placement

- **Business workflow:** Internal operators define scoped, declarative order
  rules; the backend evaluates canonical facts, reduces competing actions,
  persists an explainable run/effect ledger, and blocks rate or label work when
  facts, conflicts, holds, or evaluation state are unsafe.
- **Canonical owners:** `facts.ts` owns the fact snapshot and revision;
  `evaluator.ts` owns tri-state matching; `conflicts.ts` owns deterministic
  reducers; `catalog.ts` owns the action allowlist; `orchestrator.ts` owns
  execution, idempotency, terminal audit-only behavior, and watermarks. PS-465
  exclusively owns hazmat declarations, immutable approved profile versions,
  optimistic writes, terminal/operation locks, and rate invalidation.
- **Imperfect-data entry points:** Committed `orders`, `order_items`, and packing
  override changes enter the durable automation outbox. Missing country, PO-box,
  line, packing, workflow, and PS-465 hazmat facts remain `unknown`; compatibility
  JSON and provider payloads are not promoted to business truth.
- **Caller delegation:** Rate, Rate Browser, background rate, Shopify rate, and
  label-purchase paths call the backend preflight. React renders backend catalogs,
  traces, locks, and simulation outcomes; it does not match rules, reduce
  conflicts, select Best Rate, mint proof, or execute actions.
- **Carrier/service control owner:** `automation_shipping_controls` and
  `shipping-controls.ts` own the ordered typed exclusion records and their rate
  fingerprint. `shipping-controls-workflow.ts` owns HUGRAB policy and the
  availability read model; routes and React only pass intent/render its DTO.

## Engine and persistence

- Migration `0079_ps466_automations_engine.sql` creates relational rules,
  immutable versions, condition/action rows, runs, action results, per-order
  watermarks/plans, a durable outbox, and reprocess jobs. Migration 0078 remains
  reserved for prerequisite PS-465.
- Migration `0080_ps466_automation_recovery_leases.sql` adds expiring outbox
  and effect leases plus fencing tokens. It is additive and never updates
  orders, shipments, or provider data.
- Migration `0081_ps466_automation_shipping_controls.sql` imports active
  `shipping_automation_rules` exclusions into typed, scoped relational records,
  retains ordered/system-lock provenance, and atomically deletes the old
  settings row. Malformed JSON fails the migration before retirement.
- Published versions and their condition/action children are database-immutable.
  Publishing requires exact simulation evidence and stamps `active_from`.
- Normal event/preflight evaluation applies a rule only to orders created at or
  after `active_from`. Existing awaiting orders require the separate preview +
  confirmed bounded reprocess workflow.
- Database fact triggers enqueue committed order/item/packing changes. The worker
  claims with `FOR UPDATE SKIP LOCKED`, reclaims expired `processing` leases,
  processes at most ten reprocess orders per pass, retries with backoff, and
  dead-letters after five attempts. Completion and checkpoints are fenced to the
  current lock token.
- Execution and effect keys are unique. An effect row is atomically claimed as
  `planned` before its handler runs; failed or expired effects can be reclaimed,
  completed effects cannot, and stale owners cannot overwrite a newer lease.
- Terminal shipped/cancelled orders are audit-only. The generic action registry
  contains no purchase, void, status transition, marketplace notification,
  inventory, billing, arbitrary code, SQL, webhook, or provider-payload action.

## Supported action boundary

- Available: add tag, hold for review, require insurance with an explicit
  ParcelGuard/carrier provider, set confirmation, exclude carrier, and exclude
  service.
- Deliberately unavailable: package preset and carrier/service preference until
  their canonical package/Best Rate consumers exist.
- `hazmat.add_declaration` is wired only to the canonical PS-465 read and save
  commands. Different profile intents conflict, an existing different active
  declaration requires operator review, and the command records immutable rule,
  effect, and profile-version provenance while retaining PS-465's terminal,
  operation, feature-flag, and optimistic-revision guards.
- The execution context carries the caller's canonical `ClientStoreScope` into
  every action handler. Request-driven hazmat writes preserve that restricted
  scope; only explicitly trusted internal workers originate with global scope.
- Label preflight passes its opaque, same-order purchase-lease capability to
  nested hazmat work. PS-465 verifies that the capability was issued by the lock
  owner and is still active, preventing non-reentrant reacquisition without
  weakening purchase serialization.
- Deliberately unavailable in the production catalog: no compliance-approved
  immutable Leeds Line declaration profile has been supplied. The profile
  registry is intentionally empty, so validation rejects the action rather than
  inventing regulated shipping facts. Test-only synthetic profiles prove the
  delegation boundary without entering production configuration.
- Shopify runs the same preflight but fails closed when the reduced plan contains
  shipping actions its provider path cannot consume.

## Operations Console and Guided Builder

- Adds a top-level Automations workspace with rule search/list/inspector, carrier
  and service controls, run history, and the backend action registry.
- Rehomes the legacy Settings automation entry as a compatibility link; the old
  URL redirects to `/automations`.
- Carrier/service controls read and write only `/automations/controls`; the
  singular `/automation` API and settings-backed service are deleted. A runtime
  scanner in the mandatory SOT guard pack blocks reintroduction.
- Guided Builder uses backend field/operator/action catalogs and an explicit
  Basics -> Conditions -> Actions -> Review flow. Line predicates are emitted
  with explicit same-line `line_any` semantics.
- Draft writes use ETag/`If-Match`; simulation reports zero writes and zero
  provider calls; publish defaults to future orders only.
- The offline Playwright suite verifies desktop operations, guided simulation and
  publish, protected HUGRAB controls, run history, unavailable PS-465 hazmat, and
  a 390px mobile builder. It generates local screenshots under `reports/ps-466/`.

## Lockdown proof

Per user override `unlock shipped data` on 2026-07-25, the following
shipped-adjacent surfaces were changed:

- `src/services/labels.ts` - runs automation preflight under the existing label
  purchase lock, verifies the ruleset digest sealed into a selected rate, and
  now reads carrier/service exclusions from the typed PS-466 owner.
- `src/routes/labels.ts` - maps automation preflight/proof blocks to an
  operator-actionable HTTP 409.
- `src/services/order-hazmat.ts` - adds PS-466 decision provenance to the
  existing required PS-465 audit event; terminal and label-operation guards are
  unchanged and still execute before any write. It may reuse only a validated
  same-order outer purchase lease; standalone saves still acquire their own.
- `src/lib/label-purchase-lock.ts` - validates an opaque issued lease by order,
  token, release state, and expiry before nested canonical work may reuse it.
- `drizzle/0079_ps466_automations_engine.sql` - order status changes can enqueue
  automation audit evidence; the trigger never rewrites an order or shipment.

Protections not weakened:

- `src/routes/orders.ts`, `src/services/fulfillment-deductions.ts`,
  `web/src/components/Views/OrdersView.tsx`, `src/db/schema/orders.ts`, and
  `src/db/schema/shipments.ts` are untouched.
- Existing shipped/cancelled guards run before automation label preflight.
- Automation tag mutation rechecks the canonical order status under a
  transaction advisory lock and rejects terminal orders.
- No SQL UPDATE/DELETE targets real shipped/cancelled orders or shipments.


Docker and a standalone local PostgreSQL server are unavailable in this
workspace; the migration proof uses the PostgreSQL-compatible PGlite engine and
exercises DDL, triggers, CHECK constraints, immutable-version failures, unique
idempotency/outbox keys, activation indexes, expired/live lease selection,
stale-owner fencing, ordered control import, carrier-optional service parity,
system provenance, atomic settings retirement, and exclusion-only constraints.

The repository-wide master profiles are not clean on the unchanged base. Their
representative PS-050, PS-051, carrier-recipient, and label-scope failures were
reproduced in the other stable/PS-465 worktrees and are not caused by PS-466.
The very long all-safe profile was stopped after reaching those baseline browser
failures; it is not reported as passing evidence.

No real rate/label provider, postage purchase, label print, marketplace
notification, inventory deduction, production migration, or production
order/shipment mutation was performed.
